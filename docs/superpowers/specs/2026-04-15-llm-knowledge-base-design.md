# LLM 知识库设计方案

**日期：** 2026-04-15  
**状态：** 已在对话中确认方向，现整理为书面评审稿  
**范围：** 一个以文件夹、Markdown、`registry` 索引层和 Codex 工作流为核心的轻量级本地知识库 MVP

---

## 1. 目标

构建一个轻量、清晰、有层次的 LLM 知识库，用于长期积累和整理论文、博客、知乎文章、微信公众号文章、GitHub 材料、小红书内容以及本地文档。

这个系统需要满足以下目标：

- 让新内容进入知识库的过程足够顺滑、低摩擦
- 在条件允许时尽量保留原始资料
- 把零散内容规范化为统一的知识卡片
- 通过分层检索支持问答，而不是每次都重读整个知识库
- 支持基于历史积累做查询、综合、对比和深入思考
- 保持实现简单，能够直接基于文件夹、Markdown 和 Codex app 运转

本期 MVP 明确不引入数据库、向量库或 Web 应用等重基础设施。

---

## 2. 产品原则

### 2.1 保持轻量

知识库必须可以作为一个普通本地目录直接使用。关键内容都应该是人类可读、可编辑、可迁移的文本文件，而不是依赖专有系统。

### 2.2 明确区分来源、理解和导航

系统不应把原始材料、理解性笔记和索引元数据混放在一起。

- `sources/` 负责保存原文和快照
- `notes/` 负责沉淀理解后的规范化内容
- `registry/` 负责导航、筛选和分层检索

### 2.3 第一优先级是快速入库

第一版设计应优先保证“内容能顺利进库”。结构可以逐步完善，但不能因为过度设计拖慢积累过程。

### 2.4 用分层检索替代全库扫描

问答时不应该默认读取整个知识库，而应采用逐层收缩上下文的方式：

1. 先查轻量 `registry`
2. 再选少量相关 `notes`
3. 只有必要时才回看 `sources`

### 2.5 为后续升级留余地

目录和元数据结构需要支持未来升级，例如 SQLite、向量检索、关系图谱等，但这些能力不应成为第一版的前置条件。

---

## 3. 推荐的 MVP 架构

MVP 采用四层文件式知识系统：

1. `inbox/`：低摩擦输入层
2. `sources/`：原始资料保真层
3. `notes/`：规范化知识卡片与综合笔记层
4. `registry/`：轻量导航与检索路由层

Codex 作为工作流编排者，负责入库、规范化、问答和综合整理。

### 3.1 为什么采用这个结构

这个结构兼顾了简单性和长期可维护性：

- 纯文件结构便于查看、迁移和手工修订
- `registry` 提供了层次感和可控检索范围
- 标准化卡片减少重复阅读原文的成本
- Codex 提供灵活的推理和整理能力，而不需要额外搭建复杂后端

## 4. 目录结构

```text
llm_knowledge/
  inbox/
    links/
    files/
  sources/
    papers/
    blogs/
    social/
    github/
    snapshots/
  notes/
    atomic/
    syntheses/
    topics/
  registry/
    entries/
    topics/
    tags/
    sources/
    timelines/
  templates/
  docs/
```

### 4.1 `inbox/`

用途：低摩擦入口区。

- `inbox/links/` 用于暂存待处理链接或链接清单
- `inbox/files/` 用于暂存待处理文件或文件引用

规则：

- 用户不需要在输入时先决定最终归档位置
- `inbox` 中的内容要么被处理进正式结构，要么明确保留为待处理状态

### 4.2 `sources/`

用途：保存原始资料或尽力保留的本地快照。

建议子目录：

- `papers/`：论文 PDF、附录、补充材料
- `blogs/`：博客导出文本或清洗后的网页快照
- `social/`：知乎、微信公众号、小红书等内容
- `github/`：README、issue、设计文档、关键仓库上下文
- `snapshots/`：通用网页正文或其他不便直接分类的抓取结果

规则：

- 能保留原文就尽量保留
- 无法完整保留时，至少记录来源链接和基础元信息
- `sources/` 以保真为主，不承载知识整理逻辑

### 4.3 `notes/atomic/`

用途：最小稳定知识单元。

每一篇 `atomic` 笔记通常对应一条来源内容或一个范围很小的来源集合，至少应包含：

- 摘要
- 核心观点
- 证据
- 相关性
- 个人思考
- 后续线索

问答时优先消费这一层，而不是直接阅读原始资料。

### 4.4 `notes/syntheses/`

用途：跨多篇内容的综合笔记。

适合沉淀例如：

- RLHF 的演进脉络
- agent memory 的主要分歧
- 推理模型训练方案的比较

### 4.5 `notes/topics/`

用途：长期维护的主题页。

例如：

- `agents`
- `post-training`
- `evaluation`
- `data-engineering`

主题页更像地图页，承担稳定导航、结构梳理和关联入口的作用，链接 `atomic` 与 `syntheses`。

### 4.6 `registry/`

用途：轻量的检索路由和导航元数据层。

它应当“便于快速读取”，而不是承载长内容。

- `registry/entries/`：每条知识条目的轻量索引
- `registry/topics/`：按主题聚合的入口页
- `registry/tags/`：按标签聚合的入口页
- `registry/sources/`：按来源平台、作者或仓库聚合
- `registry/timelines/`：按时间线组织主题演进

## 5. 数据模型

### 5.1 全局唯一标识

每一条知识内容都应有稳定的 `id`。

`id` 是以下对象之间的主键：

- 原始来源记录
- `atomic` 笔记
- `registry` 条目
- 主题页与综合页中的反向关联

推荐格式：

```text
<type>-<year>-<month>-<slug>
```

示例：

- `paper-2026-04-scaling-test-time-compute`
- `blog-2026-04-karpathy-knowledge-workflows`
- `github-2026-04-openai-evals-notes`

### 5.2 内容类型

建议的顶层内容类型：

- `paper`
- `blog`
- `social`
- `github`
- `note`
- `doc`

### 5.3 完整笔记的元数据字段

每条规范化笔记的 frontmatter 至少应包含：

- `id`
- `title`
- `type`
- `source_kind`
- `authors`
- `created_at`
- `source_url`
- `local_source_paths`
- `topics`
- `tags`
- `status`
- `importance`
- `related`

后续可按需要扩展：

- `published_at`
- `language`
- `institution`
- `confidence`
- `review_state`

### 5.4 `registry` 条目的元数据字段

`registry` 条目应当短小、偏检索，不应复制完整笔记正文。建议字段包括：

- `id`
- `title`
- `type`
- `topics`
- `tags`
- `source_kind`
- `created_at`
- `card_path`
- `source_paths`
- `summary`

## 6. 标准 `atomic` 卡片模板

每一条新来源通常都应对应一份带 YAML frontmatter 的 Markdown 卡片。

建议模板：

```md
---
id: paper-2026-04-example
title: Example Title
type: paper
source_kind: arxiv
authors: [A, B]
created_at: 2026-04-15
source_url: https://example.com
local_source_paths:
  - /abs/path/to/source.pdf
topics: [agents, post-training]
tags: [memory, planning]
status: distilled
importance: high
related:
  - synth-agent-memory-overview
---

# Summary

一句话摘要 + 一段短摘要。

# Core Claims

- 观点 1
- 观点 2
- 观点 3

# Evidence

- 关键证据、实验或论据
- 哪些是强结论，哪些只是推测

# Relevance

这条内容为什么值得进入长期知识背景。

# My Thoughts

个人判断、不确定点、与已有认知的联系或冲突。

# Follow-ups

- 后续问题
- 相关论文
- 相关仓库
```

### 6.1 采用这个模板的原因

这个模板已经足够支持检索、问答和后续综合，但仍保持轻量，适合高频入库。

它正好对应你选择的“标准卡片”粒度：

- 摘要
- 核心观点
- 证据
- 关联主题
- 个人思考

## 7. `registry` 设计

### 7.1 `entries` 层

每一条规范化笔记都应同步生成或更新一份 `registry/entries/` 记录。

这份索引回答的问题应是：

- 这条内容是什么
- 主要讲什么
- 完整卡片在哪
- 原始来源在哪
- 最短可用摘要是什么

### 7.2 `topics` 层

每个 `registry/topics/` 文件建议维护：

- 主题简介
- 代表性条目
- 重要综合页
- 关键分歧或未解问题
- 必要时的推荐阅读顺序

这样在回答主题类问题时，可以先从这里获得地图，而不是一上来翻很多 `atomic`。

### 7.3 `tags` 层

标签索引结构更弱、更灵活，适合跨主题聚合。

例如：

- `alignment`
- `rag`
- `eval`
- `agent`
- `memory`

### 7.4 `sources` 层

来源索引支持按以下维度聚合：

- 平台
- 作者
- 机构
- 仓库

这有助于回答：

- 某个作者在不同文章里都表达了什么观点
- 某个仓库中有哪些值得进入知识库的材料

### 7.5 `timelines` 层

时间线索引用于记录某个主题或方法的演化顺序。

适合：

- 论文发展脉络
- 方法谱系
- 早期观点与后期观点的比较

## 8. 入库流程

第一版要优先做好“快速、顺滑地新增内容”。

### 8.1 支持的输入形式

MVP 应支持：

- 一个网页链接
- 一个本地文件路径
- 一个 PDF
- 一段粘贴文本
- 一个 GitHub URL
- 一个已有条目 ID（用于补充或修订）

### 8.2 入库阶段

1. 接收输入
2. 识别来源类型
3. 尽量保留原始资料
4. 提取最小元信息
5. 生成 `atomic` 卡片草稿
6. 更新 `registry`
7. 视情况提示更新主题页或综合页

### 8.3 来源分类

每个输入项首先应被分类为：

- `paper`
- `blog`
- `social`
- `github`
- `doc`
- `note`

这个分类会决定默认归档目录和抽取方式。

### 8.4 原始资料保留策略

当前已确认采用“尽力保留”的策略：

- 能本地保存原文时就保存
- 不能保存时，至少保存链接、元信息和尽力生成的本地快照

这在简单性和资料保真之间取得了比较合理的平衡。

### 8.5 双模式入库

当前已确认采用双模式：

- 默认快速路径
- 长内容确认路径

#### 快速路径

适用于普通来源内容。

行为：

- 创建来源记录或本地快照
- 创建 `atomic` 卡片
- 创建 `registry` 条目
- 更新相关的主题、标签、来源索引

#### 确认路径

适用于较长、较难、较关键的内容，例如：

- 长论文
- 长技术博客
- 复杂 GitHub 仓库
- 多文档组合材料

行为：

- 先解析并生成摘要草稿
- 给出建议主题和标签
- 等待用户确认
- 确认后再正式写入卡片和索引

这样既保证了日常内容能快速进入知识库，也能在复杂材料上保留质量控制。

## 9. 检索与问答策略

系统不应在每次问答时读取整个知识库。

### 9.1 分层检索

推荐的检索顺序：

1. 先搜索 `registry/`
2. 再选择少量相关 `notes/`
3. 仅在必要时回看 `sources/`

### 9.2 常规上下文规模

对一般问题，推荐读取：

- 3 到 8 篇 `atomic` 笔记
- 视情况补充 1 到 2 篇 `syntheses` 或 `topics`

这样既能保证回答有依据，也能避免上下文膨胀。

### 9.3 何时读取原始来源

只有在以下情况才回看原始资料：

- 笔记中信息不足
- 需要精确措辞或直接证据
- 用户明确要求来源级验证
- 多篇笔记之间存在冲突或不确定性

### 9.4 回答结构

回答时应尽量区分：

- 来自现有笔记的结论
- 基于这些结论的综合推理
- 当前仍不确定或证据不足的部分
- 引用到的条目 ID 或文件路径

这样知识库才能真正成为思考辅助系统，而不是模糊搜索层。

### 9.5 查询模式

MVP 内部建议支持四种工作模式：

- `lookup`：定位条目、定义、出处、时间线节点
- `brief`：基于少量笔记快速作答
- `synthesis`：跨多条内容做总结、比较、归纳
- `deep-think`：在已有知识基础上做更强的推演和思考

用户不需要每次手动指定，但 Codex 内部应按这类方式组织回答流程。

## 10. Codex 工作流入口

MVP 应优先约定一组高频、简单、可复用的操作，而不是设计复杂界面。

### 10.1 核心操作

建议最小集合为：

- `ingest`
- `normalize`
- `ask`
- `synthesize`
- `trace`

### 10.2 各操作语义

#### `ingest`

输入：链接、文件、文本或仓库引用  
输出：尽量保存原始资料，生成 `atomic` 卡片，并更新 `registry`

#### `normalize`

输入：已经存在于 `inbox/` 或 `sources/` 的待处理内容  
输出：补齐标准卡片和索引元数据

#### `ask`

输入：自然语言问题  
输出：基于选中笔记给出回答，并说明使用了哪些条目

#### `synthesize`

输入：某个主题或一组条目  
输出：新的综合页，或对主题页进行刷新

#### `trace`

输入：一个结论、一段摘要或一个条目 ID  
输出：这个结论对应的笔记和来源路径

### 10.3 输出约定

为了保持工作流透明，每次操作都应尽量返回：

- 新建或修改了哪些文件
- 使用了哪些条目 ID
- 回答是否只基于笔记，还是回看过原始来源

## 11. 命名与落盘约定

### 11.1 `atomic` 笔记

建议命名：

```text
notes/atomic/<id>.md
```

### 11.2 `registry/entries`

建议命名：

```text
registry/entries/<id>.md
```

### 11.3 主题页

建议命名：

```text
notes/topics/<topic-slug>.md
registry/topics/<topic-slug>.md
```

### 11.4 综合页

建议命名：

```text
notes/syntheses/<theme-or-question>-<date>.md
```

命名规则优先考虑稳定、可搜索和可理解，而不是追求花哨。

## 12. MVP 边界

为了让第一版保持可落地，MVP 明确不做：

- 数据库
- 向量库
- Web 服务或后台界面
- 复杂爬虫基础设施
- 自动知识图谱生成

这些能力未来可能有价值，但不应阻塞第一版起步。

## 13. 推荐实施顺序

### 第一阶段：搭骨架

创建：

- 目录结构
- 模板文件
- 命名规则
- 元数据约定

### 第二阶段：打通入库主链路

支持：

- 输入链接或本地文件
- 原始资料落盘
- `atomic` 卡片生成
- `registry` 条目生成

这一步是对当前目标最关键的部分。

### 第三阶段：补检索和综合

支持：

- `registry` 优先搜索
- 小范围笔记选择
- 基于笔记的回答生成
- 主题页与综合页更新

### 第四阶段：后续增强

可以考虑的升级方向：

- 更好的去重
- 更丰富的主题关系
- SQLite 元数据层
- 向量辅助召回

## 14. 关键风险与缓解方式

### 风险 1：入库流程变得过重

如果卡片模板过于复杂，用户会不愿意持续把内容放进知识库。

缓解方式：

- 保持 `atomic` 卡片标准化但尽量紧凑
- 只在复杂资料上启用确认路径

### 风险 2：`registry` 逐渐失真

如果索引层不能在每次入库后同步更新，检索质量会快速下降。

缓解方式：

- 把更新 `registry` 作为每次入库的固定步骤
- 保持索引文件结构最小化

### 风险 3：主题结构失控

如果每次都随意新增主题，会导致主题页混乱。

缓解方式：

- `topics` 保持相对克制和人工治理
- `tags` 负责更灵活的弱结构化聚合

### 风险 4：回答超出证据边界

如果系统不区分“卡片已有结论”和“后续推理”，综合回答会逐渐失真。

缓解方式：

- 明确区分事实、解释和推断
- 在需要精确性时使用 `trace` 并回看来源

---

## 15. 最终建议

最适合当前目标的 MVP 是：

- 基于文件夹
- 基于 Markdown
- 由 `registry` 辅助检索
- 以快速入库为第一优先级
- 由 Codex 驱动工作流

这个方案足够轻，可以马上开始；同时又足够有结构，能逐渐长成长期个人知识系统。

它直接对应你的核心诉求：

- 系统性整理零散知识
- 不必每次重读全库
- 更容易和你自己的知识背景同步
- 给链接或文件后能快速归档
